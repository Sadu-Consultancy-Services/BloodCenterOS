1. Overview & Conventions
BloodCenterOS uses a PostgreSQL schema without Entity Framework. All business logic is written as Stored Procedures / Functions called from .NET 10 (ASP.NET Core Web API + MVC) through ADO.NET / Dapper. Every business table carries a CenterId for multi-center (multi-tenant) isolation. Tables are snake_case in the base schema, while newer patch tables use PascalCase — this inconsistency itself is a cleanup candidate.

2. End-to-End Data Flow (Blood Center Management Lifecycle)

High-Level Flow

Setup & Masters→ Donor Registration→ Screening / Deferral→ Camp / Collection→ Blood Bag Entry→ Testing & QC→ Component Prep→ Inventory Stock→ Reservation / Crossmatch / Issue→ Billing / Payment→ Returns / Discard→ Reports & Compliance

Two parallel procurement paths feed stock: (A) In-house donation (donor → collection → testing → components) and (B) Mother Blood Bank reception (BloodReception → auto component creation). Stock then flows through reservation (FIFO), crossmatch, issue (to hospitals/patients or external storage units), billing, and finally returns/discards.

  1. System Setup & Master Data — Admin creates the center (BloodCenterMaster), branches, departments, designations, employees, devices & fridges. Users are created (UserMaster) with roles & permissions (RolePermissionMap, UserRoleMap, CenterUserMap). Reference data seeded: states/cities/pincodes, blood groups, lookup types/values, reasons, holidays, component types, test kits, service charges and rates (RateMaster).
  2. Donor Registration — DonorMaster is the single donor registry. Registrations can be walk-in, replacement (ReplacementDonor), or camp-based (CampDonorMap).
  3. Pre-donation Screening — Vital signs & eligibility checked into DonorHealthHistory. If ineligible, a DeferralRecord is created (temporary/permanent). Appointment optional via DonorAppointment. DonorDonationHistory is the per-donor donation ledger.
  4. Camp Planning & Execution — BloodCampMaster (+ CampOrganizer) schedules events; CampInventory allocates bags/consumables and CampExpenseLog tracks costs.
  5. Blood Collection — CollectionRecord captures the donation event (donor, camp, bag number, volume, phlebotomist); staff mapped via CollectionStaffMap. A BloodBagMaster row (unique bag no + barcode) is created and linked to the donor.
  6. Mother Blood Bank Reception (Procurement) — BloodReception / BloodReceptionDetail record received bags; the SP fn_blood_reception_create auto-creates donors, bags, donation history, components (WB/PCV/FFP/PC by bag type) and updates InventoryStock in one transaction.
  7. Testing & Quality Control — BloodTestRecord (header) + BloodTestResult (HIV, HBsAg, HCV, VDRL, Malaria) per bag. Reactive units are segregated. Laboratory reagent QC logged in QCRegister (Pool Cell, Anticera, Saline, Copper Sulphate, Coombs/AHG, BSA); device QC in QualityControlRecord. Kits tracked via TestKitMaster, technicians via TestTechnicianMap.
  8. Component Preparation — ComponentPreparation (+ ComponentPreparationLog) converts a whole bag into components; each resulting unit becomes a ComponentMaster row with status Available. Storage location recorded in ComponentStorage / fridges. InventoryStock is updated (available/reserved/issued counts by component × blood group).
  9. Hospital / Patient Request & Reservation — Hospitals register in HospitalMaster. Requests come as PatientRequest (classic flow) or PatientReservation + ReservationDetail (newer FIFO booking flow, patch-007) where fn_reservation_create allocates the oldest-expiring available components and marks them Reserved. Emergency needs handled via EmergencyRequest / EmergencyDonorResponse. Status transitions logged in RequestStatusLog.
  10. Crossmatching — CrossMatchEntry (header) + CrossMatchTestResult run Saline / Bovine / Coombs tests per reserved component; overall result Pass / Reject. (Legacy CrossMatchRecord overlaps — see review.)
  11. Issue — After crossmatch pass, components are issued to hospitals/patients via IssueRecord, or to external storage units via IssueStorage + StorageMaster. Component status → Issued; stock updated.
  12. Billing & Payment — BillingTransaction (invoice header) + InvoiceDetail (line items) + PaymentRecord. Rates come from RateMaster / ServiceChargeMaster. Dues register & credit notes are computed against these tables. Payables to Mother Blood Banks recorded in MbbBill / MbbBillDetail. General operations costs in ExpenseMaster.
  13. Returns, Discards & Destruction — Unused/returned units: ReturnRecord. Unsuitable/reactive/expired units: DiscardRecord with disposal/autoclave tracking.
  14. Store Inventory (Non-blood) — Reagents & consumables managed separately in InvItems / InvTrans (inward/outward with min-order validation).
  15. Communication & Notifications — SMS/email via templates (SmsTemplateMaster, EmailTemplateMaster), sent messages logged to OutboxLog / DonorCommunicationLog; in-app alerts in NotificationMaster; feedback & newsletter subscriptions stored.
  16. Reporting & Compliance — Summaries via report SPs (donor, camp, inventory, blood stock, procurement); export/upload logs (ExportFileLog, MonthlyReportLog, DataUploadHistory, PortalUploadQueue); cached dashboard metrics in AnalyticsDashboardData.
  17. Security & Audit — LoginHistory, AuditLog, ChangeLog, ErrorLog, BackupLog, SchedulerJobLog; API integrations via ApiIntegrationMaster / ApiResponseLog; numbering via SequenceCounters; config via SystemConfig / CenterConfig; attachments in AttachmentStore.

Key Status Lifecycle for a Blood Component

Collected / Received→ Quarantined→ Tested & Released → Available→ Reserved→ Crossmatched → Issued→ Returned / Discarded

Stored in ComponentMaster.CurrentStatus (Available / Reserved / Issued / Discarded / Transferred) and mirrored in InventoryStock counts. Every movement should also write an InventoryTransactionLog row for audit.
