Why DB Migration Order Column Mapping Code Changes Verification Pending / Follow-ups

What changed and why

PatientRequest, PatientReservation and EmergencyRequest overlapped heavily — all three described "a patient needs blood" with the same core fields (patient, blood group, units, hospital, status). Using the M9 High-priority recommendation from database_tables_data_flow_guide.html, the three were merged into a single canonical entity:

BloodRequest        (header — reservation / patient / emergency via RequestType)
BloodRequestDetail  (reserved component lines — status Reserved/Issued/Released)

Legacy CrossMatchRecord (already superseded by CrossMatchEntry + CrossMatchTestResult from Patch 008) was dropped, along with its orphaned writer SP fn_crossmatch_create.

3. Code changes

Entities (BloodCenterOS.Core)

  • PatientReservation.cs → BloodRequest.cs (new); PatientReservationDetail.cs → BloodRequestDetail.cs.
  • CrossMatchEntry, CrossMatchTestResult, IssueRecord, ReportModels updated to BloodRequestId / BloodRequestDetailId.
  • CrossMatchRecord.cs deleted (orphaned model, no live writer).

Repository & API (BloodCenterOS.API)

  • ReservationRepository / IReservationRepository — Dapper calls and result aliases use bloodrequestid / BloodRequestId.
  • Controllers (Reservation, CrossMatch, Issue, PatientRequest, Emergency, ReplacementDonor) serialize BloodRequestId in request/response DTOs.

Web (BloodCenterOS.Web)

  • ApiClient.cs — sends bloodRequestId as the JSON body property to API endpoints (Web form/action params may remain reservationId for binding; the API payload is bloodRequestId).
  • Views updated: Reservation/Index, Reservation/Details, CrossMatch/Create, CrossMatch/Details, Issue/Index, Issue/Create.
