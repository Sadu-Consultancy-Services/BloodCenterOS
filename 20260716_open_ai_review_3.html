Design Patterns

1. CRUD Pattern (4 functions per entity)

-- Typical CRUD for a business entity
CREATE OR REPLACE FUNCTION fn_donor_create(...) RETURNS BIGINT ...
CREATE OR REPLACE FUNCTION fn_donor_get_by_id(p_id BIGINT) RETURNS TABLE(...) ...
CREATE OR REPLACE FUNCTION fn_donor_update(...) RETURNS VOID ...
CREATE OR REPLACE FUNCTION fn_donor_search(...) RETURNS TABLE(...) ...

2. Business Logic Chaining

Several functions chain multiple table operations atomically:

  • fn_collection_create — inserts CollectionRecord + BloodBagMaster + DonorDonationHistory + updates DonorMaster stats in one call
  • fn_component_prepare — inserts ComponentPreparation + ComponentMaster + ComponentPreparationLog
  • fn_issue_create — inserts IssueRecord + updates ComponentMaster/BloodBagMaster status + adjusts inventory stock
  • fn_payment_create — inserts PaymentRecord + auto-updates BillingTransaction payment status

3. Sequence Number Generation

SELECT fn_sequence_next(1001, 'DonorCode');
-- Returns: "DON000001" (using prefix/suffix/increment from SequenceCounters)

4. Upsert Pattern (ON CONFLICT)

INSERT INTO InventoryStock (...)
VALUES (...)
ON CONFLICT (CenterId, ComponentType, BloodGroup)
DO UPDATE SET AvailableQty = InventoryStock.AvailableQty + p_available, ...

5. Paginated Search with Total Count

All search functions return both the page of results and a TotalCount column for UI pagination — using LIMIT/OFFSET with a separate COUNT(*) query.

6. Soft Delete via Status Fields

Instead of DELETE operations, functions update status fields (BagStatus, CurrentStatus, IsActive) to maintain audit trail.

Architecture Decision Notes

  • Functions over Procedures: PostgreSQL CREATE FUNCTION used instead of CREATE PROCEDURE because functions can return values (RETURNS TABLE, RETURNS BIGINT) and be composed in queries. The .NET/Dapper layer can call them as SELECT * FROM fn_donor_get_by_id(@id).
  • No explicit transactions: Each function runs in its own implicit transaction. Callers (application layer) can wrap multiple function calls in a BEGIN/COMMIT block if needed.
  • No foreign keys preserved: Consistent with the original design. All referential integrity is maintained by the stored procedures themselves.
  • COALESCE in updates: Update functions use COALESCE(p_param, column) so callers can pass NULL for fields they don't want to change.
  • ILIKE for search: Case-insensitive pattern matching across search functions for better user experience.
