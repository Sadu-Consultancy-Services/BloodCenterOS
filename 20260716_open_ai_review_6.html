Bugs Fixed

Bug 1: GET /api/camps/{id} — 500 Internal Server Error

Error: 42702: column reference "campid" is ambiguous — It could refer to either a PL/pgSQL variable or a table column.

Root Cause: The function fn_camp_get_by_id uses RETURNS TABLE(campid BIGINT, ...), which creates PL/pgSQL output parameters named campid, centerid, etc. The function body contained:

RETURN QUERY SELECT * FROM BloodCampMaster WHERE CampId = p_camp_id;
--                                                                  ^^^^^^ ambiguous: output parameter "campid" vs table column "CampId"

PostgreSQL could not determine whether CampId in the WHERE clause referred to the output parameter or the table column — both match case-insensitively.

Additional Issue: Even after fixing the ambiguity, SELECT * returned table columns in physical order (14 columns including StartTime, EndTime, CreatedBy), but RETURNS TABLE defined only 11 columns excluding those. Position 9 in the output was starttime (TIMESTAMPTZ) but the function expected totaldonorsexpected (INTEGER), causing "Returned type timestamp with time zone does not match expected type integer".

Fix — explicit column list + table-qualified WHERE:

RETURN QUERY SELECT c.CampId, c.CenterId, c.CampCode, c.CampName, c.OrganizerId,
                    c.Venue, c.City, c.CampDate, c.TotalDonorsExpected,
                    c.TotalDonorsCollected, c.CreatedAt
             FROM BloodCampMaster c WHERE c.CampId = p_camp_id;

File: DB/fix_camp_get_by_id.sql | Fix type: PL/pgSQL function body rewrite

Bug 2: GET /api/camps/upcoming — 500 Internal Server Error

Error: Cannot convert null to 'System.DateTime' because it is a non-nullable value type

Root Cause: The SP fn_camp_get_upcoming returns only 6 columns (campid, campname, venue, city, campdate, totaldonorsexpected), but the C# repository's GetUpcomingAsync method attempted to map 14 properties including createdat (non-nullable DateTime), which the SP does not return:

return rows.Select(r => new Camp {
    CampId = (long)r.campid,
    CenterId = (long?)r.centerid,        // not in SP → null, OK (nullable)
    CampCode = (string?)r.campcode,      // not in SP → null, OK (nullable)
    ...
    CreatedAt = (DateTime)r.createdat,   // not in SP → null → CRASH!
    ...
});

Fix — only map columns the SP returns:

return rows.Select(r => new Camp {
    CampId = (long)r.campid,
    CampName = (string?)r.campname,
    Venue = (string?)r.venue,
    City = (string?)r.city,
    CampDate = (DateTime?)r.campdate,
    TotalDonorsExpected = (int?)r.totaldonorsexpected
});

File: BloodCenterOS.API/Repositories/CampRepository.cs line 69

Pattern Insight

⚠ PL/pgSQL RETURNS TABLE × Dapper dynamic mapping — recurring hazard

These bugs are the same class as the earlier fn_donor_get_by_id fix. When using RETURNS TABLE(colname TYPE, ...) in PostgreSQL:

  1. Ambiguous column references — output parameter names shadow table columns; always qualify with table name/alias
  2. Column order mismatch — SELECT * returns physical table order; RETURNS TABLE may define a different subset/order; always list columns explicitly
  3. Dapper dynamic + missing columns — C# repository code must only reference columns the SP actually returns; accessing a missing dynamic property yields null, which crashes on non-nullable casts like (DateTime)null
